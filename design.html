실제 운영 전환 설계

현재 통합업무지시 솔루션은 서버 없는 프론트엔드 데모입니다. 여러 사람이 동시에 쓰고, 로그인으로 본인이 확인되고, 새 지시가 실제로 알림이 가게 하려면 무엇을 더 지어야 하는지를 정리한 설계 문서입니다. 코드가 아니라 결정과 구조를 다룹니다.

현재 상태 목표 아키텍처 데이터 모델 인증·인가 알림 API 전환 로드맵 인프라 옵션 결정 필요 사항

현재 상태 (베이스라인)

지금 배포된 버전이 실제로 어떻게 동작하는지부터 정확히 짚습니다. 아래 4가지가 "운영 전환"의 출발선입니다.

영역현재한계
데이터 저장브라우저 메모리(JS 변수)의 orders · staff 배열새로고침하면 초기화, 다른 사람 화면과 공유 안 됨
"로그인"담당지사 · 역할 · 담당구역을 화면에서 직접 선택본인이 누구인지 확인하는 절차가 없음 — 아무나 아무 역할을 고를 수 있음
관리자 권한고정 비밀번호 문자열 비교 (0303)페이지 소스에 그대로 노출, 브라우저에서만 검사되어 우회 가능
사진 · 첨부파일FileReader로 읽은 base64 데이터를 메모리에만 보관세션 종료·새로고침 시 소실, 다른 사람에게 전달 안 됨
알림같은 화면 안 탭에 빨간 숫자 배지화면을 열어두지 않으면 새 지시가 왔는지 알 방법이 없음
!
즉, 지금은 "혼자 켜놓고 보는 화면"입니다. 여러 지사·여러 직원이 동시에 같은 데이터를 보고 쓰려면, 그 데이터가 사는 곳(서버·DB)이 브라우저 바깥에 있어야 합니다. 아래 설계는 전부 이 한 문장에서 출발합니다.

지금의 JS 배열을 실제 테이블로

인증 · 인가

"역할 선택"에서 "로그인"으로

가장 중요한 원칙: 서버가 강제해야 진짜 보안입니다. 지금은 화면(프론트엔드)에서만 데이터를 필터링하고 있어서, 개발자 도구를 열면 원칙적으로 누구나 다른 지사·다른 사람의 데이터에 접근할 수 있는 코드 구조입니다. 로그인이 생기면 이 필터링을 서버 쪽으로 옮겨야 의미가 있습니다.

  1. 로그인

    사번(또는 이메일) + 비밀번호로 로그인. 사내 SSO(구글 워크스페이스 · AD)가 있다면 자체 비밀번호 없이 그쪽에 위임하는 편이 관리 부담이 적습니다.

  2. 세션 발급

    로그인 성공 시 서버가 JWT(또는 세션 쿠키)를 발급. 토큰 안에 user_id, 현재 활성 role·branch_id·zone_id를 담습니다. 겸직자는 로그인 후 "역할 전환" UI로 여러 user_roles 중 하나를 고를 수 있게 하면 지금의 역할 선택 UX를 유지할 수 있습니다.

  3. 모든 API 요청에 토큰 첨부

    브라우저는 요청마다 토큰을 함께 보냅니다. 지금처럼 scope.branch를 브라우저가 스스로 선언하는 게 아니라, 서버가 토큰에서 읽은 scope로 응답을 필터링합니다 — 클라이언트가 무엇을 요청하든 서버가 최종 결정권을 가집니다.

  4. 관리자 권한 재설계

    고정 문자열 비밀번호(0303) 대신 users.is_admin 플래그 + 별도 로그인 또는 2단계 인증(OTP)으로 전환. 관리자의 모든 수정 · 삭제는 audit_log에 자동 기록해 "누가 언제 무엇을 바꿨는지" 추적 가능하게 합니다.

알림

화면을 안 열어도 알게 하기

지금의 배지는 "화면을 이미 열고 있을 때"만 보입니다. 실제 현장 인력은 이동 중이거나 대기 중일 때가 많으므로, 화면 밖에서도 오는 알림이 필요합니다.

단계별 전환 순서

한 번에 다 바꾸지 않고, 화면은 거의 그대로 둔 채 뒤에서부터 순서대로 실체를 채워가는 방식을 제안합니다.

  1. Phase 0 — 완료

    프론트엔드 프로토타입: 역할별 화면, 담당구역, 인사이트, 관리자 모드, 수행 등록 UI. 지금 배포된 상태입니다.

  2. Phase 1 — 백엔드 · DB 구축

    위 데이터 모델대로 API 서버 + PostgreSQL 구축. 프론트엔드는 orders·staff 배열을 직접 조작하던 곳을 fetch 호출로 교체. 로그인 없이 관리자 도구로만 데이터 확인 가능한 상태.

  3. Phase 2 — 로그인 · 인가 도입

    실 계정 로그인, 서버 측 scope 강제. 화면 상단의 "역할 선택 드롭다운"은 로그인 사용자의 실제 user_roles 목록으로 바뀌거나, 관리자 전용 "다른 사용자로 보기" 기능으로 남습니다.

  4. Phase 3 — 파일 스토리지 연동

    사진 · 첨부파일을 오브젝트 스토리지에 실제 업로드. 지금의 base64 미리보기 로직은 업로드 진행 표시로 대체.

  5. Phase 4 — 알림 연동

    웹푸시부터 시작해 카카오 알림톡 · SMS 순으로 확장. 카카오 사업자 인증 · 템플릿 심사는 이 단계 착수와 동시에 별도로 신청(리드타임이 있어 병행 필요).

  6. Phase 5 — 감사로그 · 고도화

    audit_log 기반 관리자 활동 리포트, 구역 단위 인사이트, 처리 시간(SLA) 추적 등 확장.

결정 필요

이 설계를 실행하려면 정해야 할 것들

여기서부터는 기술이 아니라 회사의 결정이 필요한 항목입니다.

  • 인프라: 클라우드 vs 온프레미스
    사내 보안 · 데이터 반출 정책에 따라 결정. 이 답에 따라 위 인프라 옵션 A/B/C가 정해집니다.
  • 로그인 방식: 자체 계정 vs 사내 SSO 연동
    SSO가 있으면 계정 관리 부담이 크게 줄어듭니다.
  • 카카오 알림톡 사업자 인증 진행 여부
    사업자등록증 · 발신 프로필 준비가 필요하고 심사 기간이 있어 조기 착수가 유리합니다.
  • 예산 · 일정
    Phase 1(백엔드·DB)만으로도 "여러 사람이 같은 데이터를 본다"는 핵심 문제가 해결됩니다 — 전체를 한 번에 하지 않고 Phase 1까지만 먼저 볼지 결정 가능.
